# Installed browser enforcement and cost protocol

## Purpose and scope

This prospective experiment checks whether the shipped Chromium extension, installed unpacked from its built distribution and registered through the repository's native-messaging installer, forwards or cancels requests through the actual browser-launched supervisor, bridge, and detector. It measures this configured local regex+NER path only. It does not estimate detector accuracy, semantic-model behavior, production reliability, or performance on other machines or browsers.

The fixed environment is the `mcr.microsoft.com/playwright:v1.63.0-noble` image and its bundled Chromium, a persistent browser context, the repository Playwright version `1.63.0`, Linux Xvfb, CPU inference, and the checked-in extension/runtime/supervisor dependencies. The Compose project is `privoke-installed-evidence`; it uses `network_mode: none`, no published ports, no credentials, no shared model or telemetry services, and a temporary browser profile. The only host bind mount is the dedicated output directory `evaluation/results/installed-browser-results`. The provider-shaped `https://chatgpt.com` endpoint is a generated-certificate local fixture resolved to loopback; any browser request to another host is recorded and fails the run. The fixture accepts only synthetic prompts and retains request bytes only in the private ignored result directory.

The extension is loaded from the actual `extension/dist` build in Chromium's persistent context, using the checked-in Chromium ID `hmlhjfklebbbhpjdjodegbjnbamlkonp`. The existing `install-native-host.sh chromium` installs the normal host manifest and launcher under the temporary XDG paths. Chromium must invoke that registered host through `chrome.runtime.sendNativeMessage`; the native host starts the detached supervisor, which owns the bridge and detector child. The runner does not start the supervisor manually or substitute a broker. Initial settings are changed using the real extension `UPDATE_SETTINGS`/`SET_MASTER_ENABLED` messages. Streamed semantic analysis stays disabled; regex and NER stay enabled for measured cases. Telemetry is disabled.

## Frozen cases and expected forwarding

Before scoring, the runner records the exact fixture prompts, source digests for the relevant shipped rules and interception code, and the expectations below. It does not tune prompts after observing a result. Cases are synthetic and are chosen only as pathway probes:

| Case | Frozen prompt | Expected action | Provider forwarding |
| --- | --- | --- | --- |
| allow | `Please explain the steps in this process.` | ALLOW | Exactly once, byte-for-byte request body preserved |
| warn | `My profile handle is @privoke_fixture.` | WARN | Exactly once, byte-for-byte request body preserved |
| block | `Contact alex@example.com about the draft.` | BLOCK | Zero requests |
| bridge/supervisor outage | Same safe ALLOW prompt while the owned supervisor is stopped | Fail-closed BLOCK | Zero requests |
| detector-only outage | Same safe ALLOW prompt while only the verified detector child is stopped | Fail-closed BLOCK | Zero requests |
| master off | Same safe ALLOW prompt after the extension disables its runtime | Bypass ALLOW | Exactly once, unchanged |
| all layers off | Same safe ALLOW prompt with all configured layers disabled | Bypass ALLOW | Exactly once, unchanged |

The fixed matrix is fetch and XHR for each of these seven cases (14 requests). An outage is induced only against a PID discovered from the supervisor/runtime's live status and verified by executable command, parent-child relationship, and `/proc` start ticks. The bridge/supervisor outage terminates only the owned supervisor, whose signal handler stops its detector child; the detector-only outage terminates only the verified detector child. The runner restores service through the extension lifecycle and records recovery before continuing. If either shipped prompt does not produce its frozen ALLOW/WARN/BLOCK action under the configured layers, the run fails; it is not relabeled.

## Evidence collection and binding

Each synthetic request uses an opaque query identifier in the fixture URL, never an action-changing body marker. The fixture records the exact method, path, request headers, and body bytes. Playwright observes the page's actual `ANALYZE_PROMPT` and `ANALYZE_RESULT` messages. A separate Chromium DevTools Protocol observer attaches to the extension service worker and records the real gRPC-Web AnalyzePrompt request/response frames. The runner decodes them with the extension's generated runtime protobuf codec, validates frame and trailer structure, and retains the RPC request ID, page request ID, exact requested layer enums, source, target app, runtime action, layer statuses, layer errors, and elapsed value. It requires `source=browser_interceptor`, the expected concrete regex+NER layer request for detector-backed cases, correct page/runtime response binding, and no omitted decode or failed observer record. Regex short-circuit may legitimately mark NER `skipped`; that status remains explicit. Master-off/all-layers-off bypass cases have no detector RPC and are validated as such. Bridge outage has an observed page analysis but no successfully completed bridge RPC; detector outage has a captured AnalyzePrompt request and an error response or gRPC trailer. No synthetic successful response is injected.

The result directory is exclusive and immutable by run: it is created only if absent. The top-level receipt ends in `complete` only when all matrix, resource, cleanup, and hash checks pass; otherwise a `failed` receipt preserves completed and failed phase records. Receipts include source, protocol, built distribution, manifest, dependency lock, native host manifest/launcher, environment-setting, prompt, and schema digests; the browser/runtime/supervisor image and version; actual PID/start-tick/socket observations; decoded synthetic-only captures; and cleanup verification. Raw prompt/capture/RPC bytes are fake-data-only and stay in ignored `evaluation/results`; logs contain no prompt or body content. The output volume is the only persistent mount. External provider traffic, a wrong extension ID, missing native launch evidence, listener leakage before a cold session, process identity mismatch, undecoded RPCs, request-layer mismatch, action/forwarding mismatch, source drift, or inability to cleanly stop owned processes fails the run.

## Cost measurements

The cold-start sample has 12 fresh persistent profiles and fresh owned process lifecycles: two sessions for each of the six fetch/XHR × ALLOW/WARN/BLOCK cells. Before each session, ports 8080, 50056, and 50057 must be closed, and no process matching this run's Chromium profile, installed native host, supervisor entry point, or detector entry point may remain. The installed host registration is shared in the temporary XDG config root; each browser profile itself is unique and disposable. Startup intervals are reported separately: persistent Chromium launch to its extension service worker, first browser-triggered native-host/supervisor/bridge readiness, supervisor-to-detector readiness, and the first detector-backed decision. Setup/status/settings requests are classified as startup/configuration, never counted as first-decision latency.

Each of the 12 sessions first runs one separate cold first-decision probe, then five unreported warmup requests and 30 sequential measured requests for its assigned transport/action cell. It runs no concurrent prompt requests. Decision latency is measured from the page's actual `ANALYZE_PROMPT` message until its matching `ANALYZE_RESULT`, before the provider round trip; the independent browser-observed total includes the forwarding response or cancellation terminal event. Runtime `elapsed_ms` is retained separately because it excludes browser and bridge round trip. Raw values are retained and p50/p95/p99 are reported for the 60 observations in each cell; the p99 is an empirical order statistic from a small sample, not a stable tail guarantee.

Resource sampling runs every 100 ms with monotonic timestamps. It records role-level RSS, PSS when Linux exposes `smaps_rollup`, and CPU time for Chromium, the native host, supervisor/bridge, and detector, keyed by PID and start ticks to avoid PID-reuse confusion. Native host is short-lived; if the sampler misses it, the report says so and does not imply its peak was measured. Supervisor and bridge share one process and are counted once. Per-role sampled peak values are not added across different timestamps. Cgroup `memory.current` and `cpu.stat` are sampled as container totals. All peaks are qualified as sampled maxima and can miss shorter spikes.

The experiment reports exact runtime image digest, bundled browser and Playwright versions, Python/package versions, spaCy model, CPU quota, visible processor count, memory limit, and backend/device settings. The fixed workload has 12 cold first-decision probes, 60 warmups, 360 measured requests, and 14 separate enforcement-matrix probes (446 requests total). Network isolation and cleanup are verified after every context and at final teardown. If the host cannot meet startup, dependency, receiver, capture, or cleanup requirements, the run is failed rather than partially promoted.

## Interpretation and official browser constraints

Playwright documents that extension testing requires a persistent Chromium context and recommends its bundled Chromium for loading extensions; this is why the harness uses `launchPersistentContext` rather than its previous browser-capture fixture ([Playwright Chrome extension guide](https://playwright.dev/docs/chrome-extensions)). Chrome documents native hosts as registered external processes using length-prefixed UTF-8 JSON over stdin/stdout, and Linux Chromium's user registration is beneath the Chromium profile configuration directory ([Chrome native messaging guide](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)). The tested extension/native host does not thereby establish compatibility with a released Chrome/Edge/Opera package.

Even a complete run proves only the observed enforcement path and bounded cost for these synthetic cases in this pinned Linux image. It does not validate classification quality, deployment or persistence across platforms, real provider traffic, semantic inference, fleet performance, or unmeasured resource spikes.
