# Installed browser enforcement and cost protocol

Protocol version: `installed-browser-enforcement-cost-v2`.

## Purpose and scope

This prospective experiment checks whether the shipped Chromium extension, installed unpacked from its built distribution and registered through the repository's native-messaging installer, forwards or cancels requests through the actual browser-launched supervisor, bridge, and detector. It measures this configured local regex+NER path only. It does not estimate detector accuracy, semantic-model behavior, production reliability, or performance on other machines or browsers.

The fixed environment is the `mcr.microsoft.com/playwright:v1.63.0-noble` image and its bundled Chromium, a headed persistent browser context under Xvfb, the repository Playwright version `1.63.0`, CPU inference, and the checked-in extension/runtime/supervisor dependencies. The Compose project is `privoke-installed-evidence`; it uses `network_mode: none`, no published ports, no credentials, no shared model or telemetry services, and a temporary browser profile. The only host bind mount is the dedicated output directory `evaluation/results/installed-browser-results`. The `/tmp` tmpfs is explicitly executable because the standard installer places the native-messaging launcher under the temporary XDG data directory there; the runner fails preflight if that launcher is not executable or its mount is `noexec`. Execution is enabled for the ephemeral `/tmp` mount to support the installer-generated launcher; the root filesystem remains read-only and other isolation settings remain unchanged. The provider-shaped `https://chatgpt.com` endpoint is a generated-certificate local fixture resolved to loopback. The controller records browser-context HTTP requests and page websocket attempts after context creation, attaching websocket observers to existing and subsequently opened pages. It does not claim observation of service-worker websocket attempts or requests before the context hook; network isolation independently prevents external egress throughout startup and execution. The fixture accepts only synthetic prompts and retains request bytes only in the private ignored result directory.

The extension is loaded from the actual `extension/dist` build in Chromium's persistent context, using the checked-in Chromium ID `hmlhjfklebbbhpjdjodegbjnbamlkonp`. The existing `install-native-host.sh chromium` installs the normal host manifest and launcher under the temporary XDG paths. For each fresh profile, the runner also binds the installer's exact host manifest into that profile's active `NativeMessagingHosts` directory before browser launch, then verifies its identity and hashes. Chromium must invoke that registered host through `chrome.runtime.sendNativeMessage`; the native host starts the detached supervisor, which owns the bridge and detector child. The runner does not start the supervisor manually or substitute a broker. Initial settings are changed using the real extension `UPDATE_SETTINGS`/`SET_MASTER_ENABLED` messages. Streamed semantic analysis stays disabled; regex and NER stay enabled for measured cases. Telemetry is disabled.

## Frozen cases and expected forwarding

Before scoring, the runner records the exact fixture prompts, source digests for the relevant shipped rules and interception code, and the expectations below. It does not tune prompts after observing a result. Cases are synthetic and are chosen only as pathway probes:

| Case | Frozen prompt | Expected action | Provider forwarding |
| --- | --- | --- | --- |
| allow | `Please explain the steps in this process.` | ALLOW | Exactly once, byte-for-byte request body preserved |
| warn | `My profile handle is @privoke_fixture.` | WARN | Exactly once, byte-for-byte request body preserved |
| block | `Contact alex@example.com about the draft.` | BLOCK | Zero requests |
| bridge/supervisor outage | Same safe ALLOW prompt while the owned supervisor is stopped | Fail-closed BLOCK | Zero requests |
| detector-only outage | Same safe ALLOW prompt while only the verified detector child is stopped | Fail-closed BLOCK | Zero requests |
| master off | Same safe ALLOW prompt after the extension disables its runtime | Bypass ALLOW | Exactly once, unchanged |
| all layers off | Same safe ALLOW prompt with all configured layers disabled | Bypass ALLOW | Exactly once, unchanged |

The fixed matrix is fetch and XHR for each of these seven cases (14 requests). An outage is induced only against a PID discovered from the supervisor/runtime's live status and verified by executable command, parent-child relationship, and `/proc` start ticks. The bridge/supervisor outage terminates only the owned supervisor, whose signal handler stops its detector child; the detector-only outage terminates only the verified detector child. The runner restores service through the extension lifecycle and records recovery before continuing. If either shipped prompt does not produce its frozen ALLOW/WARN/BLOCK action under the configured layers, the run fails; it is not relabeled.

## Evidence collection and binding

Each synthetic request uses an opaque query identifier in the fixture URL, never an action-changing body marker. The fixture records the exact method, path, request headers, and body bytes. Playwright observes the page's actual `ANALYZE_PROMPT` and `ANALYZE_RESULT` messages. A separate Chromium DevTools Protocol observer attaches to the extension service worker and records the real gRPC-Web AnalyzePrompt request/response frames. The runner decodes them with the extension's generated runtime protobuf codec, validates frame and trailer structure, and retains the RPC request ID, page request ID, exact requested layer enums, source, target app, runtime action, layer statuses, layer errors, and elapsed value. It requires `source=browser_interceptor`, the expected concrete regex+NER layer request for detector-backed cases, correct page/runtime response binding, and no omitted decode or failed observer record. Regex short-circuit may mark NER `skipped` only with the runtime's exact `Skipped after regex returned BLOCK.` reason, an error-free aggregate response, and an error-free regex layer containing a concrete BLOCK result. Master-off/all-layers-off bypass cases have no detector RPC and are validated as such. Bridge outage has an observed page analysis but no successfully completed bridge RPC; detector outage has a captured AnalyzePrompt request and an error response or gRPC trailer. No synthetic successful response is injected.

The result directory is exclusive and immutable by run: it is created only if absent. The top-level receipt ends in `complete` only when all matrix, resource, cleanup, and hash checks pass; otherwise a `failed` receipt preserves completed and failed phase records. Receipts include source, protocol, built distribution, manifest, dependency lock, native host manifest/launcher, environment-setting, prompt, and schema digests; the browser/runtime/supervisor image and version; actual PID/start-tick/socket observations; decoded synthetic-only captures; and cleanup verification. Raw prompt/capture/RPC bytes are fake-data-only and stay in ignored `evaluation/results`; logs contain no prompt or body content. The output volume is the only persistent mount. External provider traffic, a wrong extension ID, missing native launch evidence, listener leakage before a cold session, process identity mismatch, undecoded RPCs, request-layer mismatch, action/forwarding mismatch, source drift, or inability to cleanly stop owned processes fails the run.

## Cost measurements

The cold-start sample has 12 fresh persistent profiles and fresh owned process lifecycles: two sessions for each of the six fetch/XHR × ALLOW/WARN/BLOCK cells. Before each session, ports 8080, 50056, and 50057 must be closed, and no process matching this run's Chromium profile, installed native host, supervisor entry point, or detector entry point may remain. The installed host registration is shared in the temporary XDG config root; each browser profile itself is unique and disposable. Startup evidence reports persistent browser launch to extension-worker observation, settings update duration, runtime status probe duration, status-to-owned-listener verification duration, separate first-decision latency, and signed process-birth offsets. It does not report native-host/supervisor/bridge readiness or supervisor-to-detector readiness intervals because those lifecycle boundaries are not independently timed. Setup/status/settings requests are classified as startup/configuration, never counted as first-decision latency.

Each of the 12 sessions first runs one separate cold first-decision probe, then five unreported warmup requests and 30 sequential measured requests for its assigned transport/action cell. It runs no concurrent prompt requests. Browser launch, extension-worker availability, settings update, runtime status probe, and listener ownership boundaries are measured separately with a monotonic clock. Process creation offsets use the operating-system process creation timestamp and wall-clock event timestamps; they are reported as signed birth offsets, never clipped to zero, and are not readiness intervals. Decision latency is measured from the page's actual `ANALYZE_PROMPT` message until its matching `ANALYZE_RESULT`, before the provider round trip; the independent browser-observed total includes the forwarding response or cancellation terminal event. Runtime `elapsedMs` is retained separately because it excludes browser and bridge round trip. Raw values are retained and p50/p95/p99 are reported for the 60 observations in each cell; the p99 is an empirical order statistic from a small sample, not a stable tail guarantee.

Each of the twelve resource windows starts before browser startup and covers startup/configuration, the session's first decision, five warmups, and thirty measured requests. The runner closes, reaps, hashes, and validates that sampler immediately after the thirtieth measured request, before the first-session enforcement matrix and before any intentional outage, recovery, or teardown action. A failed finalization blocks the matrix and every later session. Requested start/end boundaries and the first/last observed sample timestamps are recorded separately; the sampling interval is 100 ms, so observed samples need not land exactly on either requested boundary. The 14 matrix correctness probes and all outage/recovery/teardown work are outside the resource windows and have no resource-cost claim. Session cleanup still verifies all processes, ports, and profiles after matrix activity.

Within each resource window, process and cgroup CPU usage is the nonnegative difference between that window's last and first valid counter. A window needs at least two cgroup observations; a process CPU delta is reported only when that same PID/start-tick identity has at least two observations within a window. A short-lived native host may therefore have RSS evidence but an explicitly null, unmeasured CPU delta when observed only once. The reported sampled CPU total sums these per-window deltas, never a first-to-last counter spanning the unmeasured matrix/outage gaps. Required process and cgroup counters must be present, nonnegative, and nondecreasing. Observed sample timestamps must strictly increase, remain exactly representable, and have no adjacent gap over 500 ms; otherwise the run fails. Each window reports its observed span and maximum gap, distinct from requested start/end boundaries. Memory remains a sampled maximum across observations and windows; per-role peaks are never summed across processes or timestamps. Resource sampling records role-level RSS, PSS when Linux exposes `smaps_rollup`, and CPU time for Xvfb, Chromium, the native host, supervisor/bridge, and detector, keyed by PID and start ticks to avoid PID-reuse confusion. Missing RSS/CPU/start-tick evidence fails required role evidence; unavailable PSS remains null. Native host is short-lived; if the sampler misses it, the report says it was not observed and makes no native-host peak claim. A sampled Chromium parent binding is reported when native-host parent PID and start ticks match; otherwise launch evidence is explicitly labeled as inferred from the fresh profile, registered manifest, and extension-triggered lifecycle rather than directly observed. Supervisor and bridge share one process and are counted once. Cgroup `memory.current` and `cpu.stat` are sampled as container totals. All peaks are qualified as sampled maxima and can miss shorter spikes.

Sampler finalization is a gate before the matrix or any later monitored teardown. The runner requests graceful stop, waits up to ten seconds, then requests one emergency termination and waits up to two seconds. Any termination timeout remains a failed measurement even if the emergency stop is reaped. If reaping cannot be confirmed, the receipt records unknown sampler quiescence, keeps the sampler identity/path, and blocks later monitored teardown and phase advancement; no later cleanup result can turn that window into a success. The root operator must resolve an unknown sampler before disposing the isolated run.

The experiment reports exact runtime image digest, bundled browser and Playwright versions, Python/package versions, spaCy model, CPU quota, visible processor count, memory limit, and backend/device settings. The fixed workload contains 446 page requests: 442 `ANALYZE_PROMPT` attempts (432 first-decision/warmup/measured requests plus ten detector-backed matrix attempts, including four intentional outage failures) and four bypass requests. It expects 438 successful decoded detector responses: 432 first-decision/warmup/measured responses and six successful detector-backed matrix responses; the other eight matrix probes are four bypasses and four failures, of which two are detector errors and two bridge-outage requests fail before a detector response. Network isolation and cleanup are verified after every context and at final teardown. If the host cannot meet startup, dependency, receiver, capture, resource, or cleanup requirements, the run is failed rather than partially promoted.

## Interpretation and official browser constraints

Playwright documents that extension testing requires a persistent Chromium context and recommends its bundled Chromium for loading extensions; this is why the harness uses `launchPersistentContext` rather than its previous browser-capture fixture ([Playwright Chrome extension guide](https://playwright.dev/docs/chrome-extensions)). Chrome documents native hosts as registered external processes using length-prefixed UTF-8 JSON over stdin/stdout, and Linux Chromium's user registration is beneath the Chromium profile configuration directory ([Chrome native messaging guide](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)). The tested extension/native host does not thereby establish compatibility with a released Chrome/Edge/Opera package.

Even a complete run proves only the observed enforcement path and bounded cost for these synthetic cases in this pinned Linux image. It does not validate classification quality, deployment or persistence across platforms, real provider traffic, semantic inference, fleet performance, or unmeasured resource spikes.
