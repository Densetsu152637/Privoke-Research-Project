# NER role study: amplifier or independent detector? (2026-10-24)

**Scope: detector layers only (regex + spaCy NER). This is not LLM-only or semantic evidence and not a full-product measurement.** Every prompt ran through `pipeline.analyse_text(layers=["regex","ner"], regex_first=False)` with an explicit layer list (never empty, never the semantic layer). `final.jsonl` was not opened; the harness cannot select it.

## Goal and instruction

User instruction (24 Oct 2026, program wave 1 item 5): "Test all of these in parallel and integrate promising ones"; "Ask me before any downloads". Question for this item: held-out `final` showed no net NER benefit from case preservation plus the post-filter (NER-only FP 7 to 9, recall 0.237 to 0.212, union essentially unchanged). Is NER more useful as an **amplifier of regex** (corroborating or extending regex findings) than as an independent detector?

## Method

- Script: `evaluation/ner_role_study.py` (`dump` records regex hits, NER hits and raw spaCy entities with the post-filter's corroboration features per prompt; `analyse` evaluates every policy offline from those same records). Unit tests: `evaluation/tests/test_ner_role_study.py` (synthetic records, no datasets). Host Python `evaluation/.venv-v1-v3-pipeline` (spaCy 3.7.5, `en_core_web_sm` 3.7.1; `en_core_web_lg` 3.7.1 was already installed, no download).
- Sources: NEW = `55cbd1e5` (installed defaults: case-preserving input, post-filter on; flags observed true/true). OLD = clean export of `e6c177ff` (original regex, lowercased input, no post-filter; not a git checkout). Reproduction checks: the OLD tree's shipped NER output equals raw `en_core_web_sm` entities on lowercased text for all 3502 rows (0 differences); every P0/P1 cell below equals the corresponding cell of `detector-precision-installed-20261024.md`; two independent NEW dumps gave identical regex/NER records.
- Datasets (sha256 prefixes; full hashes in the JSON): development `65bf02af`, personalized `fd045ac1`, openai `8e8e611b`. dev-TUNE/dev-CHECK by `sha256(group_id) % 2`.
- Anti-overfitting: **design splits = dev-TUNE and personalized**. The only tuned quantity is which P2 corroboration variant is called "chosen" (P2*): highest mean balanced accuracy over the design splits, ties by fewer FP. The variant set was fixed before any number was computed and all variants are in the JSON. dev-CHECK and openai are post-review (not strictly held-out: the post-filter v2 was already measured on them). Nothing was tuned on final or on check/openai.
- Positive = hit with sensitivity != S0 or with categories. P2 variants use the post-filter's own cue, recurrence and multi-token features, computed on the text the NER saw.

### Policies

| Policy | Definition |
|---|---|
| P0 | regex only |
| P1 | regex OR NER (current union) |
| P2 | regex OR (a corroborated NER entity: cue-introduced, recurring or multi-token PERSON; 6 variants, widening to place/organisation relation and locating cues) |
| P3 | NER may add categories/spans only where a regex contact/identifier finding (sensitivity >= S2) already exists |
| P4 | NER only extends the masking spans of regex-positive prompts |

**P3 and P4 cannot create a positive, so their flag decision equals P0 by construction.** Their value is masking coverage, reported in the amplification table, not recall/specificity.

### NER configurations

OLD (original tree), NEW (installed defaults, post-filtered), NEW-raw (case-preserved raw spaCy entities, no post-filter, so corroboration is the only filter), and, as a free extension, NEW@en_core_web_lg and NEW-raw@en_core_web_lg (the larger spaCy model already installed in the venv; post-filter unchanged and designed on the small model).

## Findings

1. **P3 and P4 add masking coverage but no detection.** In NEW, an extra PERSON span appears in 688 of 777 name-expected personalized rows (regex has no name rule), 9 of 21 dev-TUNE and 11 of 12 dev-CHECK name-expected rows, and an extra place span in 223 of 241 address-expected personalized rows. Extra spans in prompts expecting no PII: 0 in every NEW split. This is a real but unscored masking benefit that flag-level metrics cannot see; the e-annot span annotations are needed to score it.
2. **No P2 policy dominates the shipped union.** On the shipped (post-filtered) NEW entities P2 is a subset of P1 by construction: it only loses TP (dev-TUNE 118 to 114 positives, check 83 to 81) and removes 0 to 1 FP. The post-filter already contains the corroboration logic, so layering P2 on it is redundant.
3. **Corroboration is a cheap filter on the old pipeline.** In OLD (lowercased, unfiltered) P2* keeps 14 of the 17 union gains on dev-TUNE and drops both new FP, and on check keeps 3 of 4 gains with 0 of 4 FP. The post-filter generalised the same idea.
4. **Corroboration instead of the full post-filter is competitive, not better.** NEW-raw P2*: dev-TUNE 117 TP / 8 FP vs shipped 118 / 6 (design split, slightly worse); dev-CHECK 85 / 6 vs 83 / 6; openai 465 / 37 vs 459 / 37 (post-review, slightly better). Differences of 1 to 6 positives at n = 116 to 500 are within noise; there is no design-split basis to switch.
5. **NER as an independent detector gives a modest recall gain.** Shipped P1 over P0: +23 TP / +4 FP on dev-TUNE, +9 / +4 on check, +11 / +3 on openai, 0 / 0 on personalized. The held-out finding (no net benefit from case preservation plus post-filter) concerns that change, not NER's existence. The amplifier-only policies (P3, P4) give up all of this recall by design (negative result for "NER only when regex already fired" as a detector).
6. **`en_core_web_lg` is a free, untuned improvement on the post-review splits, not on a design split.** Post-filtered union with lg: dev-TUNE 120 TP / 7 FP (sm 118 / 6), check 87 / 2 (sm 83 / 6), openai 460 / 34 (sm 459 / 37). The design-split change is +2 TP / +1 FP, so there is no design evidence; the check/openai gain (+4 TP, -4 FP; +1 TP, -3 FP) is post-review, and all splits were inspected together. The post-filter was designed on the small model. Confirmation needs a clean split (Wave 2/3).
7. **The unfiltered union is unusable on the synthetic set**: NEW-raw P1 flags 81 of 1000 personalized negatives (specificity 0.919), which is why the post-filter exists.

## Decision on a runtime option

No cross-layer policy beat the shipped configuration on the design splits, so none was implemented. If P3/P4 masking amplification is pursued later, the interface change needed is a combination step after `analyse_text`: the pipeline runs layers independently and returns `PipelineAnalysis(layers=...)`, so a policy must receive both `LayerExecution.results` lists and return the regex-positive decision plus the union of regex and eligible NER spans for masking, with the P3 gate (regex sensitivity >= S2) evaluated there. It belongs in result-combination code, not in either detector.

One small default-off option was added so the lg result is reproducible through the product pipeline without code changes: `PRIVOKE_NER_MODEL` (`GlobalConfig.ner_model`, default `en_core_web_sm`; `EntityNERDetector(model_name=None)` reads it). Default behaviour is unchanged (tests: `extension/client-runtime/test/test_ner_model_option.py`, plus the existing NER tests, 44 pass). Spot check: with `PRIVOKE_NER_MODEL=en_core_web_lg` the pipeline reproduces the offline lg entities on the first 150 dev rows (0 differences). Docs to align when merged: `docs/detectors/ner.md` (the line stating `en_core_web_sm` is loaded) and `docs/runtime/client-runtime.md` (environment-variable list near `PRIVOKE_NER_POSTFILTER`); both are outside this task's owned paths and were not edited.

## Limitations

- Detector layer, flag-level metrics; amplification is row-level and does not score span correctness.
- Single run, no confidence intervals (see the uncertainty work in item 1); small counts on dev-TUNE/CHECK.
- check and openai are post-review; lg results were inspected on all splits at once.
- Latency not measured (timing is a serialized resource). The post-filter's `common_phrase` rule uses the loaded model's lemmatizer lexicon; lg has one.
- OLD comes from an export without git; its corroboration features are computed with the NEW tree's helpers on lowercased text.
- Reproduce: `python evaluation/ner_role_study.py dump --tree <root> --label new --extra-model en_core_web_lg --data-root <checkout> --generated <protobuf dir> --out new.json dev personalized openai` (OLD tree: same without `--extra-model`), then `python evaluation/ner_role_study.py analyse --old old.json --new new.json --out out`.
